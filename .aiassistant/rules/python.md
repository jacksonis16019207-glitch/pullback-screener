# Python コーディング規約

## 1. 基本方針

Pythonコードを新規作成・修正する際は、以下の規約を必ず遵守すること。

- 可読性、保守性、テスト容易性を優先する。
- PEP 8を基本とし、Pythonの慣用的な書き方（Pythonicな実装）を採用する。
- 型ヒントを積極的に使用し、静的型チェックが可能なコードにする。
- 関数・メソッドの責務は単一かつ明確にする。
- 不要な抽象化、過剰な汎用化、過度なネストを避ける。
- 既存のコードやプロジェクト構成、設定ファイルの規約を尊重する。
- 独自のルールとツールの設定が矛盾する場合は、明示された独自ルールを優先し、必要に応じて設定を修正する。
- 要件が不明確な場合は、勝手に仕様を追加せず、必要に応じて確認する。
- コードを生成・修正した場合は、可能な範囲で品質チェックを実行し、未実施のチェックがあれば明示する。

## 2. 命名規則

PEP 8に準拠し、以下の命名規則を使用する。

| 対象                   | 規則                | 例                       |
|------------------------|---------------------|--------------------------|
| 変数                   | `snake_case`        | `user_name`              |
| 関数                   | `snake_case`        | `fetch_data()`           |
| メソッド               | `snake_case`        | `get_user()`             |
| クラス                 | `PascalCase`        | `DataProcessor`          |
| 定数                   | `UPPER_SNAKE_CASE`  | `MAX_RETRIES`            |
| モジュール             | `snake_case`        | `data_loader.py`         |
| パッケージ             | 小文字を基本とする  | `data_processing`        |
| 型エイリアス           | `PascalCase`        | `UserId`                 |
| 型変数                 | `PascalCase`        | `T`                      |
| 内部実装用の属性・関数 | 先頭に `_` を付ける | `_cache`, `_load_data()` |
| クラス内部の属性       | `snake_case`        | `self.user_name`         |
| クラスメソッド         | `snake_case`        | `from_dict()`            |

### 2.1 命名の詳細ルール

- 名前から役割や意味を推測できるようにする。
- `a`、`b`、`tmp`、`data`、`obj` など、意味が不明確な名前を安易に使用しない。ただし、短いスコープで意味が明白な場合や、数学的な計算などでは許容する。
- 真偽値を表す変数には `is_`、`has_`、`can_`、`should_` などの接頭辞を使用する。
- コレクションには複数形を使用することを基本とする。
- 関数名は動作を表す動詞から始めることを基本とする。
- 定数はモジュールレベルで定義し、実行中に変更しない値に使用する。
- `_` から始まる名前は内部実装用とし、外部公開を意図するAPIには使用しない。
- `id`、`type`、`list`、`str` などの組み込み関数・型と同名の変数を定義しない。
- 略語は一般的なものに限定し、プロジェクト内で表記を統一する。

## 3. Docstring

### 3.1 必須ルール

- **すべての関数・メソッドにGoogle形式のdocstringを必ず付与する。**
- 公開・非公開、同期・非同期、通常メソッド・クラスメソッド・静的メソッドを問わず適用する。
- コンストラクタ `__init__` にも付与する。
- 既存コードを修正する際、docstringが存在しない対象には追加する。
- docstringは関数・メソッドの定義直後に記述する。
- docstringは日本語で記述することを基本とする。
- 関数名や型ヒントから明らかな情報を冗長に繰り返さず、目的、仕様、制約、注意点を説明する。
- 実装とdocstringの内容を一致させる。実装を変更した場合はdocstringも更新する。
- `Args`、`Returns`、`Raises`、`Yields` などの各セクションは、該当する情報がある場合に記載する。
- 型ヒントを記述していても、引数や戻り値の意味が重要な場合はdocstringで説明する。
- 引数がない場合や戻り値がない場合など、不要なセクションは省略してよい。
- クラスにもdocstringを付与し、クラスの責務と用途を説明する。

### 3.2 Google形式の基本構成

```python
def calculate_total(
		prices: list[float],
		tax_rate: float = 0.1,
) -> float:
	"""商品の合計金額を税込みで計算する。

    Args:
        prices: 商品ごとの税抜き価格のリスト。
        tax_rate: 消費税率。デフォルトは0.1。

    Returns:
        税込みの合計金額。

    Raises:
        ValueError: 税率が0未満の場合。
    """
	if tax_rate < 0:
		raise ValueError("tax_rate must be non-negative")

	return sum(prices) * (1 + tax_rate)
```

### 3.3 クラスとメソッドの例

```python
class UserRepository:
	"""ユーザー情報の取得と保存を担当するリポジトリ。"""

	def __init__(self, database_url: str) -> None:
		"""リポジトリを初期化する。

        Args:
            database_url: 接続先データベースのURL。
        """
		self.database_url = database_url

	def get_user(self, user_id: int) -> dict[str, str] | None:
		"""ユーザーIDに一致するユーザーを取得する。

        Args:
            user_id: 取得対象のユーザーID。

        Returns:
            ユーザー情報。存在しない場合はNone。
        """
		# 実際の取得処理を実装する。
		return None

	def _validate_user_id(self, user_id: int) -> None:
		"""ユーザーIDの妥当性を検証する。

        Args:
            user_id: 検証対象のユーザーID。

        Raises:
            ValueError: ユーザーIDが0以下の場合。
        """
		if user_id <= 0:
			raise ValueError("user_id must be positive")
```

## 4. 型ヒント

- 原則として、すべての関数・メソッドの引数と戻り値に型ヒントを付与する。
- インスタンス属性、クラス属性、重要な変数にも必要に応じて型を付与する。
- `Any` の使用は必要最小限にする。
- 型が不明な場合に、安易に `Any` や `object` で回避せず、実際のデータ構造を確認する。
- `None` を取り得る値は `T | None` のように明示する。
- コレクションは `list[str]`、`dict[str, int]` など、要素の型を明示する。
- 型ヒントのためだけに不要な型変換や複雑な抽象化を追加しない。
- 型アサーション（`cast()` や `# type: ignore` など）は、型チェッカーで検証できない事情がある場合に限定し、必要に応じて理由をコメントする。
- `# type: ignore` は安易に使用せず、可能な限り型定義や実装を修正して解決する。
- `ty` の型チェックを通過できることを目標とする。

## 5. 関数・メソッドの設計

- 1つの関数・メソッドには、原則として1つの明確な責務を持たせる。
- 処理が複雑になった場合は、意味のある単位に分割する。
- 引数が多すぎる場合は、データクラスなどによる集約を検討する。ただし、単純な処理に過剰なクラスを導入しない。
- グローバル変数や暗黙的な状態変更を避ける。
- 引数として渡されたミュータブルなオブジェクトを、意図せず変更しない。
- 副作用のある処理は、関数名やdocstringから動作を理解できるようにする。
- 早期リターンを活用し、条件分岐のネストを浅く保つ。
- `bool`、`None`、空文字列、空のコレクションなどの扱いを明確にする。
- 戻り値の型と意味を統一し、成功・失敗を曖昧な値で表現しない。

## 6. クラスとデータ構造

- クラスは、状態や振る舞いをまとめる必要がある場合に使用する。
- 単純なデータ保持には `dataclasses.dataclass` の使用を検討する。
- データの不変性が重要な場合は、`frozen=True` などを検討する。
- 単純な変換や計算だけであれば、クラスを作らず関数として実装する。
- 継承よりもコンポジションを優先することを基本とする。
- 継承は、明確な「is-a」関係と適切な置換可能性がある場合に使用する。
- 外部に公開するAPIと内部実装を区別する。

## 7. エラーハンドリング

- 想定されるエラーは、適切な例外で明示する。
- `except Exception:` による無差別な例外捕捉を避ける。
- 例外を捕捉した場合は、復旧、適切な変換、または必要なログ出力を行う。
- 何もせずに例外を握りつぶさない。
- 原因を失わないよう、例外を再送出する場合は `raise` を適切に使用する。
- 例外を別の例外に変換する場合は、必要に応じて `raise ... from exc` を使用する。
- エラーメッセージには、原因や対象を特定できる情報を含める。
- 入力値の検証は、処理の早い段階で行う。
- 秘密情報、認証情報、個人情報などを例外メッセージやログに出力しない。

## 8. コードの可読性

- インデントはスペース4つとする。
- 1行の長さはRuffの設定に従う。特別な設定がない場合は88文字を基本とする。
- 意味のあるまとまりごとに空行を設ける。
- コメントは、コードだけでは伝わりにくい理由や設計上の制約を説明する。
- コードの処理をそのまま日本語にしただけの冗長なコメントは避ける。
- マジックナンバーは、意味が不明確な場合に定数化する。
- 内包表記は、可読性が保たれる範囲で使用する。
- 三項演算子やラムダ式を過度にネストさせない。
- 不要なコード、未使用の変数、使用されないimport、到達不能な処理を残さない。
- 同じロジックを複数箇所に記述せず、適切な共通化を検討する。ただし、過度な共通化は避ける。

## 9. import

- 標準ライブラリ、サードパーティライブラリ、プロジェクト内モジュールの順に整理する。
- importの並び順と不要なimportの検出はRuffに任せる。
- `import *` は使用しない。
- 循環importを避ける。
- 型ヒントのためだけに必要なimportは、必要に応じて `TYPE_CHECKING` の利用を検討する。
- モジュール全体を不必要にimportせず、可読性と名前の衝突を考慮する。

## 10. 非同期処理・リソース管理

- 非同期処理が必要な場合に限り、`async` / `await` を使用する。
- 非同期関数内で、必要なく同期的なブロッキング処理を実行しない。
- ファイル、データベース接続などのリソースは、可能な限り `with` や `async with` で管理する。
- ファイルの文字コードは、特別な要件がなければUTF-8を使用する。
- タイムアウトやリトライは、外部通信など必要な箇所に限定して適切に設計する。
- リトライによる重複実行や副作用に注意する。

## 11. テスト

- 重要なロジックにはテストを作成する。
- 正常系だけでなく、異常系、境界値、空データ、`None` などのケースも検討する。
- 外部APIやデータベースなどの依存先は、必要に応じてモック化する。
- テストが実行環境や外部サービスに不必要に依存しないようにする。
- テスト名は、対象の振る舞いと期待結果が分かる名前にする。
- 既存のテストを無断で削除・弱体化しない。
- バグを修正した場合は、可能な限り再発防止のテストを追加する。
- テストを実行していない場合は、実行済みであるかのように報告しない。

## 12. uv・Ruff・ty の使用方針

### 12.1 uv

- Pythonのバージョン、依存関係、仮想環境、プロジェクトの実行には `uv` を使用する。
- 依存関係の追加・削除には `uv add`、`uv remove` を使用する。
- 開発用依存関係は、プロジェクトの構成に応じて `uv add --dev` で管理する。
- プロジェクトで管理している `pyproject.toml` と `uv.lock` を尊重する。
- 既存の依存関係を確認せずに、同等のライブラリを追加しない。
- 依存関係の更新は、必要性を確認してから行う。

### 12.2 Ruff

- LintとフォーマットにはRuffを使用する。
- Lintの指摘は、可能な限り修正する。
- フォーマットはプロジェクトのRuff設定に従う。
- ルール違反を解消するために、安易にルールの無効化や除外設定を追加しない。
- `# noqa` を使用する場合は、必要なルールIDを指定し、正当な理由がある場合に限定する。

基本コマンド：

```bash
uv run ruff check .
uv run ruff format --check .
```

自動修正・フォーマット：

```bash
uv run ruff check --fix .
uv run ruff format .
```

### 12.3 ty

- 型チェックにはtyを使用する。
- 型エラーは、可能な限り型定義や実装を修正して解消する。
- 型チェックを回避するためだけの `Any`、`cast()`、型無視コメントの追加は避ける。
- tyの設定はプロジェクトの `pyproject.toml` に従う。

基本コマンド：

```bash
uv run ty check .
```

### 12.4 品質チェックの実施順序

コードを新規作成・修正した場合は、プロジェクトで利用可能な範囲で次の順に確認する。

1. RuffのLintチェック
2. Ruffのフォーマットチェック
3. tyの型チェック
4. テストの実行

チェックに失敗した場合は、原因を確認して修正する。実行できなかった場合は、その理由と未確認の項目を報告する。

## 13. 設定ファイルの扱い

- `pyproject.toml`、`uv.lock`、`ruff.toml` など、既存の設定を優先する。
- 設定ファイルの内容を確認せずに、設定を上書きしない。
- Ruffやtyのルールを変更する場合は、変更の目的と影響範囲を確認する。
- 特定のプロジェクト固有の規約がある場合は、本規約に加えて適用する。
- ツールの設定だけでは保証できない規約（docstringの意味的な正しさなど）は、コードレビューでも確認する。

## 14. 禁止事項

以下の実装は、明確な理由がない限り禁止する。

- docstringのない関数・メソッドを作成すること。
- 型ヒントを安易に省略すること。
- 未使用の変数、import、不要な処理を残すこと。
- `except Exception:` で例外を無条件に握りつぶすこと。
- `# type: ignore` や `# noqa` を安易に使用すること。
- 組み込み関数・型と同名の変数を定義すること。
- 目的や意味が不明確な名前を多用すること。
- 要件にない機能や依存関係を勝手に追加すること。
- 既存のAPI、戻り値、例外仕様を理由なく変更すること。
- テストや品質チェックを実行していないのに、成功したと報告すること。
- エラーを隠すためだけに型チェックやLintの設定を緩和すること。

## 15. AIによる実装・修正時の最終確認

コードを提出する前に、以下を確認すること。

- [ ] すべての関数・メソッドにGoogle形式のdocstringがある。
- [ ] 命名規則に準拠している。
- [ ] 引数・戻り値などに適切な型ヒントがある。
- [ ] 関数・メソッドの責務が明確である。
- [ ] エラーハンドリングが適切である。
- [ ] 不要な処理や依存関係がない。
- [ ] 既存の仕様やAPIとの互換性を維持している。
- [ ] 必要なテストが追加・更新されている。
- [ ] RuffのLint・フォーマットチェックを確認している。
- [ ] tyの型チェックを確認している。
- [ ] 実行していないチェックを、実施済みとして報告していない。

以上の規約を、Pythonコードの生成・修正・レビュー時に適用すること。
